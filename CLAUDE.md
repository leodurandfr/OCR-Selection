# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

**OCR Selection** is a macOS menu-bar utility (a free TextSniper equivalent): press a global shortcut (default ⌘⇧2), drag-select a screen region, and the recognized text lands on the clipboard. Menu-bar only — `LSUIElement = YES`, so there is no Dock icon or main window. Targets macOS 26.0+. Distributed via **Developer ID** (the native `screencapture` dependency keeps it out of the sandboxed Mac App Store).

## Build / test / run

This is an Xcode project (not SwiftPM). Scheme: `OCRSelection`; targets: the app `OCRSelection`, the XPC service `OCRSelectionRecognizer` (embedded in `Contents/XPCServices`, built as an app dependency), and the tests `OCRSelectionTests`. Sources in [Shared/](Shared/) are compiled into both the app and the service.

```bash
# Build
xcodebuild -scheme OCRSelection -destination 'platform=macOS' build

# Run all tests
xcodebuild -scheme OCRSelection -destination 'platform=macOS' test

# Run a single test (Swift Testing path: Target/Suite/method() — the parentheses are
# required: without them nothing runs and xcodebuild still reports TEST SUCCEEDED)
xcodebuild -scheme OCRSelection -destination 'platform=macOS' test \
  '-only-testing:OCRSelectionTests/HistoryServiceTests/pruningEnforcesMaxCount()'
```

Tests use **Swift Testing** (`import Testing`, `@Test`, `#expect`) — *not* XCTest. Match that style for new tests. To run the app interactively, build & run the `OCRSelection` scheme from Xcode (⌘R) — capture and the global shortcut can't be exercised from a headless `xcodebuild` run.

Sole external dependency: [KeyboardShortcuts](https://github.com/sindresorhus/KeyboardShortcuts) (SwiftPM, 2.4.0+), resolved by Xcode.

## Architecture

`AppDelegate` (wired via `@NSApplicationDelegateAdaptor` in `OCRSelectionApp`) is the composition root: it builds the SwiftData `ModelContainer` (via `HistoryContainer.make()`), constructs the single `HistoryStore` and `CaptureCoordinator`, registers the `historyMaxCount` default, starts `HealthMonitor` and the `VisionCacheMonitor`, and binds the global shortcut to `coordinator.run()`. The SwiftUI side is just two scenes — `MenuBarExtra` and `Settings` — and **neither touches SwiftData**: both read the `HistoryStore` snapshot. A container failure logs and falls back to an in-memory store rather than `fatalError`.

**The capture pipeline lives entirely in [CaptureCoordinator](OCRSelection/CaptureCoordinator.swift).** Its `run()` is the one place that orchestrates the stateless service structs and owns all error handling, mapping typed errors to user-facing outcomes:

```
ScreenCaptureService → OCRService → PasteboardService → HistoryService → NotificationService
```

Each service is a small `@MainActor struct` conforming to a protocol seam in [OCRSelection/Capture/](OCRSelection/Capture/) (`ScreenCapturing`, `TextRecognizing`, `Pasteboarding`, `Notifying`, `HistoryRecording`, `PermissionPresenting`), so `CaptureCoordinator` can be driven with stubs in `CaptureCoordinatorTests`. Notable behaviors:

- **[ScreenCaptureService](OCRSelection/Services/ScreenCaptureService.swift)** shells out to `/usr/sbin/screencapture -i <tmpfile>` (Apple's native region selection) and decodes the PNG from that temp file, which is deleted on the way out. Outcomes: no file + preflight fails → `CaptureError.permissionDenied`; no file + empty stderr → `userCancelled` (Esc); otherwise success. It deliberately does **not** use `-c`: routing the image through `NSPasteboard` meant deep-copying and restoring the user's entire clipboard on the main thread around every capture (hundreds of MB when a large image was on it), and briefly exposed the screenshot to clipboard managers. This CLI dependency is *why App Sandbox is disabled* — the app ships via Developer ID. A ScreenCaptureKit + custom-overlay migration (needed for the sandboxed App Store) was prototyped and dropped in favour of Apple's superior native selection UI.
- **OCR runs out of process**, in the `OCRSelectionRecognizer` XPC service ([main.swift](OCRSelectionRecognizer/main.swift), [TextRecognition](OCRSelectionRecognizer/TextRecognition.swift)): Vision's `RecognizeTextRequest` (accurate, auto language detection + correction) turned into a Vision-free, Codable `RecognizedLayout` ([Shared/](Shared/)): one fragment per run of text on a visual line (a table cell, a line of one column), pixel frames, origin top-left. The image crosses XPC as raw BGRA pixels (`ImagePayload`), the layout comes back as a binary plist. Why a process: a Vision whose compiled model was purged fails with `e5rtError … 13` until its process exits (an in-process retry, even pinned to the CPU, fails the same way). **[OCRService](OCRSelection/Services/OCRService.swift)** (app side) therefore retries a Vision error or a lost connection once, transparently, on a fresh service process; a timeout (90 s per attempt — a cold compile alone is 30–60 s) restarts the service without retrying; the user is only notified if both attempts fail. **[RecognizerConnection](OCRSelection/Services/RecognizerConnection.swift)** uses the C XPC API because a restart needs the service's pid: a reconnect alone lands in the same (broken) process, so `restart` sends `quit`, waits for the pid to be gone (SIGKILL fallback), and holds new requests until then; `restartIfFailed` only restarts a connection that actually failed, so concurrent failures don't kill each other's fresh process. launchd throttles respawns to one per ~10 s, so a restart within 10 s of the service's launch delays the retry by the remainder. The service's bundle ID is the app's plus `.recognizer` (`com.leodurand.ocr-selection.recognizer`, Debug `….debug.recognizer`), so **its Vision cache is `~/Library/Caches/<service bundle ID>/com.apple.e5rt.e5bundlecache`**, not the app's. `RecognitionTransport` is the seam: `OCRServiceRetryTests` drive the retry with a stub, `OCRServiceTests` run real recognition through the real service. **Do not go back to `RecognizeDocumentsRequest`**: on the same clean image it intermittently returned only some lines, or none, depending on how Vision scheduled it (reproduced by pinning its compute device — complete by default, 461 then 0 characters on the Neural Engine, 132 on the GPU/CPU), whereas text recognition reads every line on every device. **[TextAssembler](OCRSelection/Services/TextAssembler.swift)** rebuilds the structure from geometry alone and turns it into clipboard text whose point is to *undo the wrapping of the captured region*: one line per paragraph, one per list item (markers kept, nesting as tabs), tables as tab-separated rows, side-by-side columns one after the other. It is a recursive XY cut: full-width whitespace taller than the usual line spacing separates paragraphs, full-height whitespace separates columns or cells; columns are read as text when their lines wrap (two text columns, or one whose text runs on beside the others) or when their rows don't line up once wrapped cells are put back in their row, otherwise as a table, where a wrapped cell stays one cell. Each column takes its paragraph spacing from its own lines. A line is joined to the next only on wrap evidence: the next word would not have fitted, and the next line starts in lower case or the line is long and another line of its column confirms the width (a lone widest line proves nothing — addresses, forms). A hyphen at a line end rejoins the word, except in a compound (after a capitalised word, in a word that already has a hyphen, before a capital); a dash or asterisk opens a list item only when two lines start with one. When in doubt it keeps the line break. The `preserveLineBreaks` setting (Settings → Text) bypasses unwrapping. `TextAssemblerTests` build layouts by hand, so these rules are tested without running OCR; `OCRServiceTests` run real recognition on rendered text and a borderless table.
- **Disk-full handling.** When the disk is nearly full (observed below ~20 GB free), macOS purges the service's `com.apple.e5rt.e5bundlecache` (finished models at `<OS build>/<hash>/<hash>.bundle`, in-progress compiles as `*.tmp.<pid>_*.bundle`). The purge is APFS deleting purgeable-flagged files: it removes every file and leaves the folder skeleton, so a bundle only counts when it still holds a file. Seen every few minutes at 7–8 GB free. **[VisionCacheMonitor](OCRSelection/Services/VisionCacheMonitor.swift)** prewarms at launch (a line of Latin text then one of Arabic, in the service at `.utility` priority: ~150 ms warm, ~45 s cold). The cache holds one compiled model each for text detection, orientation, and every script used — Latin and Arabic: automatic language detection was seen trying Arabic on ordinary captures, a 13–16 s compile the prewarm now takes in the background (`strings …/H16S.e5 | grep Resources/` names a bundle's model) and watches every folder of that cache with `DispatchSource` file-system sources (re-armed after each change, events coalesced over 3 s, ignored while a rebuild runs, plus a 2-minute poll); when the count of finished bundles drops while no capture is recognising (a capture's OCR recompiles the models itself, and restarting the service under it once turned a 16 s OCR into 56 s) it logs `vision cache purged`, restarts the service and prewarms again, logging `vision model ready reason=… duration=…`. None of this drives the menu-bar pulse, which is for user-initiated OCR only. If OCR still fails, or a non-first OCR takes over 10 s without having compiled a model the cache never held before (`VisionModelCaching`: another script's model, e.g. CJK or Devanagari), [DiskSpaceService](OCRSelection/Services/DiskSpaceService.swift) checks free space and the notification blames the disk. **Experiment, isolated in [VisionCacheRelocation](OCRSelection/Support/VisionCacheRelocation.swift)** (delete the file and its one call in `AppDelegate` to drop it): at launch `~/Library/Caches/<service bundle ID>` is replaced by a symlink to `~/Library/Application Support/<OCRSelection | OCRSelection Debug>/VisionCache`. Vision follows it (compiles land in the target, the next launch is warm), **but it does not protect the models**: the purge deleted the files in the target too (they carry APFS's purgeable flag, which goes wherever the file is). The `screencapture` process is killed after 5 minutes, so with the OCR timeouts `CaptureGate.isBusy` can't stay stuck.
- **History** is three pieces. [HistoryContainer](OCRSelection/Support/HistoryContainer.swift) builds the store at `~/Library/Application Support/OCRSelection/History.store` (a bare `ModelContainer(for:)` defaults to `default.store` in the *shared* Application Support root; a store found there is migrated once, then deleted) and sets `mainContext.autosaveEnabled = false` — the autosave timer saved on the main thread and was the heaviest stack in a `cpu_resource` report. [HistoryService](OCRSelection/Services/HistoryService.swift) owns every `ModelContext` call; `record` prunes past `historyMaxCount` (a `UserDefaults` key, default 30, user-adjustable 10–50) using `fetchOffset` so only doomed rows are fetched. [HistoryStore](OCRSelection/Services/HistoryStore.swift) is the `@Observable` snapshot of `HistoryItem` values the UI renders. **Do not put `@Query` in the `MenuBarExtra`**: its body is re-evaluated far more often than the menu is opened, and each evaluation meant a SwiftData fetch. `OCREntry` is the lone SwiftData `@Model`.

## Diagnostics

The app is instrumented for after-the-fact debugging of intermittent slowdowns ([PerfLog.swift](OCRSelection/Support/PerfLog.swift)). Everything diagnostic is logged at `.notice` or `.error` — `.info`/`.debug` are not persisted to disk and are useless the next morning. Never log recognised text, only lengths.

```bash
# What the app recorded (per-capture timings + 60s health heartbeat)
log show --last 1d --predicate 'subsystem BEGINSWITH "com.leodurand.ocr-selection"' --style compact
```

`HealthMonitor` writes one heartbeat per minute: `mem=` (phys_footprint) exposes a leak, `menuRenders=` exposes a SwiftUI render storm, `lag=` and gaps between heartbeats expose a blocked main thread.

The app can't log while it is wedged, so for anything the heartbeat can't explain, use what macOS collects on its own — `*.cpu_resource.diag` microstackshot reports land in `/Library/Logs/DiagnosticReports/` when a process exceeds 50% CPU over 180s, and `JetsamEvent-*.ips` there records footprints at memory-pressure kills. Live, on a misbehaving process: `sample OCRSelection 10 -f /tmp/ocr.txt` and `footprint OCRSelection` (both work on the Developer ID build without root).

## Conventions

- **Localized strings**: all user-facing text goes through `String(localized:)` / SwiftUI auto-localization, backed by `Localizable.xcstrings`. Supported languages: **EN, FR, ES** — add new strings to all three. Source-comment language is mixed (some French); follow the file you're editing.
- Bundle ID `com.leodurand.ocr-selection`; copyright/about links point at leodurand.com. The **Debug** configuration is a separate app — `com.leodurand.ocr-selection.debug`, shown as "OCR Selection Debug", default shortcut ⌘⌥⇧2, logs under its own subsystem, history in `Application Support/OCRSelection Debug/`, its own recognizer service `com.leodurand.ocr-selection.debug.recognizer` (and so its own Vision cache), and never migrates the legacy `default.store` — because sharing one bundle ID with the installed Developer ID build made them steal each other's Screen Recording grant (TCC binds it to one signature) and one ⌘⇧2 start two captures (and, with split `historyMaxCount` defaults, a shared store would let one prune the other). Query both with `subsystem BEGINSWITH "com.leodurand.ocr-selection"`.
- Preferences "Launch at login" uses `SMAppService.mainApp`.
